## Что уже работает

- Создание LAN-комнаты с названием и кодом минимум из шести символов; обнаружение комнат и ручное подключение по IP:port.
- Текстовые и голосовые каналы, профиль/переименование, список участников, сообщения, пагинация истории, переподключение.
- История, каналы и файлы сохраняются в SQLite/каталоге данных создателя; он должен оставаться включённым.
- Голосовые звонки, приглашения с явным согласием до включения микрофона, mute/deafen, завершение и повторный вход.
- Камеры, отдельная демонстрация окна/экрана, одновременная работа камеры и экрана.
- Крупный просмотр видео/демонстрации. Esc закрывает просмотр, но сохраняет сам звонок и захват.
- Передача файлов до **2 ГиБ** потоком, SHA-256, системный диалог сохранения, атомарная публикация/сохранение; полученные файлы не открываются автоматически.
- Русский тёмный интерфейс с янтарным акцентом, настройки имени и адреса комнаты.

Установщики и исполняемые файлы пока не подписаны. **Захват системного звука не реализован**: при демонстрации передаются изображение экрана и отдельно микрофон.

## Архитектура и файлы

| Часть | Назначение |
| --- | --- |

| `assets/` | HTML, CSS, иконки; `assets/pkg/` — генерируемые WASM bindings |
| `scripts/build.mjs` | Сборка WASM, bindings и native Rust-сервиса |
| `tests/e2e/spark.spec.cjs` | Три поддерживаемых сквозных сценария Electron/Playwright |
| `scripts/test-linux.mjs`, `e2e-linux.sh` | Изолированные Linux E2E: Xvfb, D-Bus, XDG-каталоги, оконный менеджер |

| `SPEC.md` | Подробный HTTP/WS/media-контракт; сведения о владении агентами там исторические |

Приложение написано на Rust, включая клиентскую логику и WebRTC. UI компилируется в WebAssembly; JavaScript в Electron обеспечивает интеграцию с ОС. Это **не полностью нативные Rust-виджеты**. Chromium выбран ради одинакового WebRTC на Linux и Windows; замена оболочки требует проверки media/capture на обеих платформах.

Каждый клиент запускает собственный Rust-сервис на случайном порту **127.0.0.1**. Он отдаёт UI и API, обеспечивает доверенный локальный origin для разрешений браузера. Создатель дополнительно поднимает LAN-host. Данные сервиса находятся в `core/` внутри Electron userData; тесты используют отдельные временные каталоги. Для изоляции доступен `SPARK_DATA_DIR`, но не подставляй реальный профиль пользователя в автоматические тесты.

## Сеть и границы безопасности

- LAN-host: **TCP 39393** по умолчанию.
- Обнаружение: **UDP 23994**. Старое значение 39394 намеренно заменено: оно попадало в ephemeral-диапазон и конфликтовало на ноутбуке с чужим системным сокетом.
- Медиа: прямой WebRTC mesh с динамическими UDP-портами, без STUN/TURN, аккаунтов, облачного relay или телеметрии.
- Ручное подключение должно работать, даже если UDP discovery недоступно.
- На компьютерах может потребоваться разрешение приложения в брандмауэре частной сети. Изоляция Wi-Fi-клиентов/гостевая сеть мешает прямой связи. Это не повод менять настройки без задачи пользователя.
- Чат и файлы идут по HTTP/WebSocket внутри доверенной LAN и **не имеют сквозного шифрования**. Код комнаты ограничивает вход; он не заменяет шифрование транспорта. WebRTC-медиа используют DTLS/SRTP.
- Loopback API проверяет Host/Origin и локальный nonce. Renderer изолирован: sandbox, contextIsolation, без Node integration; произвольная навигация запрещена.
- Не ослабляй эти проверки ради удобства тестов. Не публикуй токены, ключи, локальную историю, данные комнаты и реальные снимки рабочего стола.

## Сборка

Нужны Rust stable **1.88+**, target `wasm32-unknown-unknown`, Node.js **24+**, npm, **wasm-bindgen-cli 0.2.130**, системные библиотеки Electron. На Windows — Rust MSVC и Visual Studio Build Tools с C++; Linux и Windows пакуются на соответствующей ОС.

**Проверка ПК по SSH на 2026-11-11, только чтение:** пользователь `eugheist`, хост `archlinux`, `~/src` существует. Обнаружены Git 2.55.0, Node 26.9.0, npm 12.0.2 и системный Arch Cargo 1.98.1 (`/usr/bin/cargo`). `rustup` и `wasm-bindgen` в PATH не найдены. Есть `xvfb-run`, `dbus-run-session`, `kwin_x11`; Openbox не обнаружен. **На ПК Spark ещё не собирали и не тестировали.** Ничего не устанавливали и приложение не запускали.

Поэтому сначала проверь `rustc --version`, `rustc --print sysroot` и доступность target/std для `wasm32-unknown-unknown`, способ управления системным Rust и наличие CLI `wasm-bindgen` версии 0.2.130. Не предполагай, что `rustup` уже установлен или что ноутбучный путь Cargo подходит ПК. Не ставь параллельный toolchain без проверки существующей конфигурации.

Пример последовательности **для окружения, где Rust уже управляется rustup**:

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.130 --locked
npm ci
npm run build
npm start
```

Это команды для будущей задачи сборки; не выполняй установку автоматически только при чтении handoff. Альтернатива долгой установке CLI из исходников — `python scripts/install-bindgen.py`: скачивает официальный закреплённый бинарник для Linux/Windows x64 и сверяет опубликованный SHA-256. Версия CLI должна соответствовать Cargo.lock.

На ноутбуке Cargo находился в `~/.cargo/bin` вне обычного PATH; `build.mjs` сам добавляет этот каталог. На ПК проверь реальные пути. `npm ci` запускает явный Electron postinstall — у закреплённого Electron 45 скачивание бинарника иначе может не выполниться.

```sh
npm run package:linux
# На Windows:
npm run package:win
```

Результаты в `dist/`: Linux AppImage/TAR.GZ, Windows NSIS setup.exe/ZIP. Сначала `npm run build`, затем упаковка. Не публикуй старые `dist/`-файлы после изменения исходников. `target/`, `node_modules/`, `assets/pkg/`, `desktop/binaries/`, `dist/` и тестовые артефакты — генерируемые данные, не исходники.

## Обязательная проверка изменений

```sh
cargo test --locked -p spark-protocol -p spark-service
cargo fmt --all -- --check
cargo clippy --locked -p spark-protocol -p spark-service --all-targets -- -D warnings
cargo check --locked -p spark-ui --target wasm32-unknown-unknown
npm run build
```

На Linux E2E запускай **только через изолирующий wrapper**:

```sh
npm run package:linux
SPARK_PACKAGED_BINARY="$PWD/dist/linux-unpacked/spark-lan" npm run test:e2e:linux
```

Нужны Xvfb, D-Bus и тестовый WM (wrapper поддерживает доступный KWin/Openbox). Прямой `npm run test:e2e` на живом Linux-дисплее может затронуть реальный рабочий стол — так не проверяй захват.

Windows CI после `npm run package:win` использует PowerShell:

```powershell
$env:SPARK_SKIP_SCREEN_TEST = '1'
$env:SPARK_PACKAGED_BINARY = "$PWD\dist\win-unpacked\Spark.exe"
npm run test:e2e
```

Флаг пропуска экрана честно оставляет физический Windows-захват непроверенным; не превращай его в универсальное решение ошибок. `SPARK_E2E_MEDIA=1` включает синтетические камеру/микрофон **только в распакованной dev-сборке**, в packaged-приложении игнорируется. Не включай реальные устройства в автоматических тестах. Отчёты/скриншоты — `test-results/` и `playwright-report/`.

## Важные исправленные ловушки — не возвращать

1. **`web_sys::MediaStream.clone()` — браузерный метод**, создающий копии реальных tracks. Для сохранения ссылки на тот же JS stream используй **`Clone::clone(&stream)`**. Иначе preview/sender/cleanup расходятся, и оригинальные камера/экран продолжают работать после завершения. Тестируй identity и `readyState` первоначального track.
2. Нативный `onended` может уже стоять в очереди, когда Rust-closure удалена. Используются browser-owned closures через `into_js_value`, weak-ссылки, epoch/current-track/current-peer guards; поздний callback безопасно игнорируется. Не возвращай callback-after-drop или удержание устройств через цикл ссылок.
3. Только детерминированный offerer заранее создаёт audio/camera/screen transceivers; answerer принимает входящие и привязывает локальные tracks. Если обе стороны независимо создадут их, можно получить одностороннюю передачу. ICE restart ограничен, stale ufrag/candidates фильтруются.
4. Media DOM и `srcObject` сохраняются при обновлении presence/чата. Пересоздание видео на каждом событии рвёт воспроизведение. Большой просмотр не должен останавливать звонок при закрытии.
5. Не держи `RefCell` borrow во время замены DOM: change/blur могут синхронно вызвать обработчик и привести к `BorrowMutError`. Сначала снимок состояния и освобождение borrow, затем render. Прогресс файла обновляет только meter, не весь composer.
6. Discovery обновляет только свою область, отсеивает устаревшие запросы и не стирает введённые имя/код/адрес. Connect читает актуальные видимые поля.
7. Wayland не должен вызывать два последовательных portal picker: обход `getSources` и передача `{video: {id: 'screen:0:0', name: ...}}` делегируют выбор системному порталу один раз. На X11/Windows перечисляются реальные окна/экраны; выбор одноразовый, связан с requesting frame и имеет таймаут.
8. При завершении host нужно дождаться остановки UDP advertiser, чтобы порт освобождался. Native-тесты discovery сериализованы из-за общего порта.
9. На Windows `DirEntry.metadata().len()` может отставать, пока upload writer открыт. Fixture проверки отмены читает реальный первый байт как сигнал записи, а не доверяет устаревшему размеру.
10. Файлы не буферизуются целиком в Rust/WASM: upload/download streaming, лимит, хеш, временный файл и атомарная финализация. Ошибка/отмена не должна публиковать недокачанный файл или портить существующий destination.

## Релизы и происхождение 0.1.0

Основной workflow собирает обе платформы, тестирует **распакованные и packaged** приложения, сохраняет пакеты/evidence. Теги `v*` включают release job после обеих платформ. Для уже проверенных артефактов есть `publish-verified.yml`: проверяет приватность репо, успешные платформенные jobs, равенство кода приложения, имена/размеры четырёх пакетов, SHA-256; сначала создаёт draft и только после проверок публикует.

У **0.1.0** Windows job `130601184168` в run `43043486238` успешен, но общий run позднее отменили из-за зависшего Linux APT mirror. Linux recovery run `43046329617`, job `130611351172` полностью успешен; отличие только в workflow. Publisher run `43047982286` успешно выпустил обе платформы. Поэтому одна отменённая верхнеуровневая сборка не означает отсутствие Windows-проверок.

APT в актуальном `build.yml` уже ограничен таймаутами, использует официальные Ubuntu HTTPS-источники, IPv4 и noninteractive-режим. Не убирай эти ограничения без причины: выбранное hosted image Azure HTTP-зеркало зависало. Это CI-настройки, не инструкция менять репозитории пакетов на ПК пользователя.

При следующем релизе обновляй согласованно версии Cargo/npm и lock-файлы, release notes; публикуй только новые пакеты проверенного кода. Не перезаписывай выпущенный 0.1.0 и не используй старые default inputs publisher без сверки текущих run/SHA/version. Готовый проверенный релиз разрешено выпускать без повторного вопроса пользователю.
